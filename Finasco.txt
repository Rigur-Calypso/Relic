 P1. Gemini model names in the PRD are retired / closed to new users
--------------------------------------------------------------------------------
 Problem  : The PRD specifies `gemini-2.0-flash` (default) and `gemini-2.5-flash`
            (drop-in upgrade). Both fail today:
              - gemini-2.0-flash -> 404 "no longer available"
              - gemini-2.5-flash -> 404 "no longer available to new users"
 Impact   : Every AI call (extract, heal, diff) threw 404 until fixed.
 Fix      : Switched to `gemini-3.6-flash` (the API's own recommended replacement,
            identical call signature). Set via GEMINI_MODEL in .env.
 Status   : RESOLVED. .env default is gemini-3.6-flash.
 Fallback : `gemini-flash-lite-latest` also works and has a SEPARATE quota bucket
            (see P2) — used as the overflow model during the big run.

--------------------------------------------------------------------------------
 P2. Gemini free-tier daily quota (20 requests/day PER MODEL) is too small
--------------------------------------------------------------------------------
 Problem  : Free tier caps generate_content at 20 requests/day/model. A full
            9-site run is ~25+ AI calls (9 scrape + up to 9 wayback + 9 diff),
            plus debugging calls. We hit HTTP 429 RESOURCE_EXHAUSTED mid-run:
              "Quota exceeded ... limit: 20, model: gemini-3.6-flash"
 Impact   : - Full pipeline cannot complete on one model in one day.
            - The dashboard's live Scrape/Heal/Analyze buttons will fail once the
              day's 20 calls are spent (they spawn scripts that read .env).
 Fix      : Split the load across two models with independent buckets:
            gemini-3.6-flash + gemini-flash-lite-latest. The last full data run
            was generated on gemini-flash-lite-latest after 3.6-flash was spent.
 Status   : RESOLVED via multi-key rotation. src/gemini.js now accepts a pool of
            free-tier keys (GEMINI_API_KEYS=key1,key2,...) and auto-rotates to the
            next key on a quota error, persisting which keys are spent
            (data/.gemini-state.json) across the separate scrape/wayback/analyze
            processes, resetting at Pacific midnight. Invalid keys are skipped;
            transient 5xx are retried on the same key. With 7 keys the pool gives
            ~140 calls/day — the full 9-site pipeline ran end-to-end on
            gemini-3.6-flash with zero manual intervention (rotation fired twice
            mid-run and continued seamlessly).
 NOTE     : Enabling BILLING on one key is still the cleanest long-term fix, but is
            no longer required to run or demo the project.

 P5. archive.org Wayback Availability API rate-limits our IP (HTTP 429)
--------------------------------------------------------------------------------
 Problem  : GET https://archive.org/wayback/available returned an HTML
            "429 Too Many Requests" page instead of JSON, so res.json() threw
            "Unexpected token '<'" for EVERY target. Direct backoff (up to 45s)
            did not clear it — the IP throttle lasts minutes.
 Fix      : Rewrote src/analyzer/wayback.js:
              1. Try the Availability API first (gives the exact capture date);
                 short backoff, then give up fast.
              2. FALLBACK: fetch the Wayback redirect
                 http://web.archive.org/web/<ts>000000/<url> THROUGH BRIGHT DATA.
                 Bright Data's proxies bypass the IP-level 429, so history keeps
                 flowing. Added not-archived detection + empty-content guards so
                 missing captures degrade to "no snapshot" instead of crashing.
 Status   : RESOLVED. On-theme bonus: even the history layer is now
            Bright-Data-resilient (a stronger hackathon story).
 Note     : records carry snapshotVia = "availability-api" (exact ts) or
            "brightdata-redirect" (ts labeled ~YYYYMMDD, approximate).

 P10. Scaling from 9 -> 22 monitored labs
--------------------------------------------------------------------------------
 Goal     : Add many more top-college core/nanofab facilities.
 Method   : Because URLs can't be guessed reliably (P3), a discovery script
            (scratchpad/discover.mjs) ran `bdata search` for 30 institutions,
            picked the first non-junk result URL, and scored each page's equipment
            density with a keyword heuristic — ALL via Bright Data, ZERO Gemini —
            so only pages that actually list instruments were committed.
 Result   : 16 of 30 passed; 3 (upenn/mitnano/epfl) were dropped after the real
            Gemini scrape extracted 0 (their pages describe the facility but don't
            expose an extractable instrument list). Net +13 = 22 targets, ~800+
            instruments, 8 knowledge-loss cases (added JNCASR -10, UCSB -6,
            IIT-KGP -4, Notre Dame -3).
 Gotchas  : (a) `bdata search` table output truncates long URLs — two were fixed
            to full URLs. (b) zsh does NOT word-split unquoted $VAR, so
            `for id in $LIST` ran once with the whole string; used literal lists.
 Frontend : With 22 cards the sidebar got long — reworked App.jsx into a proper
            app shell (fixed header + independently scrolling columns) and added a
            "N labs monitored / M with knowledge loss" header stat.

--------------------------------------------------------------------------------
 P11. Scaling from 22 -> 101 monitored labs
--------------------------------------------------------------------------------
 Goal     : Push past 100 labs.
 Method   : Two more discovery sweeps (~190 institutions total via bdata search +
            keyword probe, zero Gemini) yielded 79 new validated pages -> 101.
            A resumable orchestrator (scripts/run-remaining.mjs) runs
            scrape->wayback->diff only for targets missing an analysis file, so it
            survives interruptions and quota ceilings.
 Quota    : The full run needed ~250 Gemini calls — more than one model's 7x20=140
            free-tier ceiling. Hit the cap on gemini-3.6-flash mid-run; the NEW
            per-model quota tracking (gemini.js) let the SAME 7 keys keep going on
            gemini-flash-lite-latest (its own 140-call bucket). Finished all 101
            in-day across both models.
 Data-qual: Fixed a real bug — when a live scrape extracts 0 (or a thin landing
            page), the diff would falsely report "total knowledge loss". Added a
            guard in diff.js (empty current -> skip) and suppressed 2 thin-scrape
            artifacts (Harvard CNS, Northwestern NUANCE) that mislabeled loss.
 Speed    : archive.org's availability API always 429s from one IP; removed its
            slow backoff so wayback drops straight to the Bright-Data-proxied
            redirect. Made make-static-data.mjs skip unparseable files so a push
            during an active run can never break the Vercel build.
 Result   : 101 labs, 2,556 instruments, 62 real diffs, 28 knowledge-loss cases.
